# MRP 格式规范：已验证的索引型变体

## 0. 适用范围与证据

本规范针对本仓库归档的 [打包器](mrc/mrp.c)、[读取器](mythroad/mythroad.c)以及本次 664 个文件、96,856 个索引项的语料。**实测**只覆盖对应的样本和运行环境；**源码**只说明这份归档实现；**待验证**不是其他实现的保证。它不是所有历史 MRP 变体的完整标准；664 包的离线重建不代表它们已运行，另有源码包的独立 WASM 实验见 1.5。

完整逐项结果由 [工具](../../tools/mrp_tool.py)生成到本地的 [JSON 档案](../../build/mrp-research-v3/mrp_catalog.json)；每包 SHA-256、逐项偏移和压缩验证结果均在其中。汇总结论与复现命令见 [研究报告](MRP_RESEARCH_REPORT.md)，历史手册交叉对照见 [文档笔记](OFFICIAL_DOCS_NOTES.md)。同仓库 Guest 二进制与归档源码是否完全对应，仍待验证。

## 1. MRPG 包

### 1.1 头部

**源码 + 实测：**语料全为 `4d 52 50 47`（`MRPG`）。下表是该打包器的布局；未列出的字节保留原样，不作通用解释。整数大小和端序不能由字符串的 GBK 编码推断。

| 偏移 | 宽度 | 解释 |
|---:|---:|---|
| `0x00` | 4 | ASCII `MRPG` |
| `0x04` | 4 LE | `X`；索引结束的绝对偏移为 `X + 8` |
| `0x08` | 4 LE | 声明的包长度；不得小于索引和所引用的数据末尾 |
| `0x0c` | 4 LE | 索引起始绝对偏移 |
| `0x10` | 12 | 内部文件名，NUL 填充 |
| `0x1c` | 24 | 应用显示名，GBK/NUL 填充 |
| `0x44` | 4 LE | 应用 ID 的一份表示 |
| `0x48` | 4 LE | 版本的一个表示 |
| `0x54` | 4 LE | 一部分包的头部 CRC32 字段；算法及范围见 1.4 |
| `0x58` | 40 | 厂商名，GBK/NUL 填充 |
| `0x80` | 64 | 描述，GBK/NUL 填充 |
| `0xc0` | 4 BE | 应用 ID 的另一份表示 |
| `0xc4` | 4 BE | 版本的另一份表示 |
| `0xf0` | — | 此打包器的固定头部结束、通常也是索引起点 |

12/24 字节由 `mrc/mrp.c` 实际写入，不能统一改写成 16 字节内部名。两套 ID/版本可能不一致；应同时保留原始头部。包显示名是**头部元数据**，与每个资源的索引文件名相互独立。

`mrper.mrp` 声明 45,927 字节、物理 45,959 字节；`MRPPT.mrp` 声明 32,929、物理 32,944。末尾分别有 32/15 字节未计入声明长度。工具保留它们；它们的用途和在修改内容后是否涉及签名**待验证**。

### 1.2 索引

从 `index_start` 遍历到 `X + 8`，端点不包含在内。每项：

```text
u32le N | N 字节名称字段 | u32le 数据绝对偏移 | u32le 存储字节数 | u32le 保留
```

总长为 `16 + N`。名称一般是 GBK 加 NUL，查找时按第一个 NUL 前的字节进行精确比较；`applist.mrp` 的 `start.mr` 名称字段有**两个**尾随 NUL。读取器先清零临时名称缓冲，因此不能假定所有变体的 `N` 一定恰好为 `strlen + 1`。索引中保留字段在 96,856 项中均为 0，但其在其他包的含义未知，不能写死。

**边界：**检查 `index_start <= X+8 <= declared_size <= physical_size`、每项长度、`offset >= index_end`、以及无整数溢出的 `offset + stored_size <= declared_size`。工具当前允许 `1 <= N < 256` 以检查数据；这份原生读取器的 `MR_MAX_FILENAME_SIZE` 为 128，实际查找要求 `N < 128`。普通目录打包遵循较小的运行时限值；保留更长名称的已解包 manifest 会发出警告。语料中最长名称按常规单 NUL 计为 37 字节。

重复名称不合并、不排序：例如 541 包含多个精确入口；VM 按索引顺序返回**第一个与请求名称完全相同**的项。文件扩展名、大小写折叠结果不能代替实际查找。初筛请求 `start.mr`，不存在时才请求 `start.m`；另有一个包只有 `_start.mr`，不能静默改写入口。

### 1.3 数据区与写入

索引的 `offset` **直接指向存储数据**，不需要跳过额外前缀。该打包器另外在数据前写一份顺序记录：

```text
u32le N | 原始 N 字节名称字段 | u32le 存储字节数 | 存储数据
```

它用于顺序旧式/RAM 读取；新索引读取以索引为准。`X + 8` 是索引之后的第一个顺序记录起点，而不是第一条资源正文起点。将合成包的 `X` 改为 `X-1` 或 `X+1` 时，本工具的有界解析均失败；这是 Python 检验，**不是**运行时篡改实验。

可按上述结构写出固定头部、索引、顺序记录；回填三个小端头字段和索引偏移。保留名称字段的原始字节、重复项、非零保留值、压缩流和末尾额外字节，不能仅按文件名字典重建。**实测：**对全部 664 包按索引/记录重建得到字节完全相同的包；其中 5 个真实包还完成了解包 → 打包 → 再解包，原包、存储数据及解码数据逐字节一致。未对全部 664 包执行后者，也未执行游戏。

归档 `_mr_readFile` 另有 `headbuf[1] <= 232` 的**旧式 MRPG 顺序记录分支**，以及 `*A`/`$` 内存分支；本工具不宣称实现所有这些旧变体。664 个语料均为可解析的索引型 MRPG。

### 1.4 头部 CRC32：不可普遍假定

`[源码引用]` 固定提交的 SDK `mrpbuilder.py` 在新建头部时将 `0x54..0x57` 初始化为零，再对 `filehead + indexbuf + filesbuf` 计算 `zlib.crc32` 并以小端写入该字段；来源和哈希见 [文档笔记](OFFICIAL_DOCS_NOTES.md)。因此对于这类新包，校验时将该四字节视为零，对完整物理文件计算 CRC32。此处是**整包头部字段**，与每个 gzip trailer 的 CRC 是两个不同校验。

`[实测]` 664 包对该字段作互斥比较：

| 匹配 | 包数 | 含义 |
|---|---:|---|
| `builder-crc32` | 448 | 物理文件范围吻合 |
| `declared-crc32` | 1 | `mrper.mrp` 仅按声明长度计算时吻合，物理文件另有 32 字节 |
| `zero` | 9 | 字段全零 |
| `unknown` | 206 | 非零且与上述两种计算均不符 |

`unknown` 不等于必然损坏，也不能断言这些包使用同一种其他算法或签名方案。工具在 manifest 中保存识别模式：原样往返保持字节；内容变化时，已识别的两种 CRC 重新计算，零值保留，未知非零值原样保留并警告。旧 manifest 没有模式时按未知值处理；`--force-builder-crc32` 会**显式覆盖**并按完整物理文件计算，只有确认目标格式时才使用。普通目录新建包使用 builder 模式。扫描结果的 `header_checksum` 和 `header_checksums` 可逐包复查。

### 1.5 源码入口包：用户样本与 WASM 复测

`[实测]` 本次取得的用户 `demo.mrp` 为 **444 字节**，SHA-256 `6b62eea8b2ae26d9f0c38822f104ab2f15f1725972e8930e8f1914b07c309926`，索引从 `0xf0` 到 `0x122`。`0x04` 的 `0x11a` 是 `0x122 - 8`，不是通用格式版本；仅有一个入口的方言探针包此字段为 `0x101`。两个资源如下：

| 名称 | 数据偏移 | 存储字节 | 解压后 | 类型 |
|---|---:|---:|---:|---|
| `mythroad` | 307 | 20 | 0 字节 | gzip，空内容 |
| `start.mr` | 344 | 100 | 92 字节 | gzip，脚本源码 |

该样本 `0x2c/0x30` 各写了 1000，也在 `0x44/0x48` 写了同样值；前两处落在本节 12/24 字节布局的**显示名区域**，不能据此作为通用 ID/版本字段。[固定提交的 SDK 打包器](https://github.com/vmrp/MythroadSDK/blob/2df8647d674b8da1f8fff91d6c84f177efb5ae16/mrpbuilder.py#L465)在 `0x34` 起写入九个 `g_host_auth_str` 字符，不能仅凭当前样本将其认作整包校验和；已识别的整包 CRC 字段是 `0x54`，此样本那里为零。

用户记录描述过 506 字节、绿色画面的版本；当前提供的文件解出 92 字节源码，清屏 `(10,20,30)` 并绘制红字，因此两者不能当作同一字节样本。按记录中的 20 字节 marker、96 字节入口及对应记录长度相加为 `240 + 50 + (17 + 20) + (17 + 96) = 440` 字节，不能单独推出 506 字节；差额成因待取得对应原文件后核对。

`[源码引用]` [mrp_load](mythroad/src/mr_api.c) 看首字节是否为签名首字节，[f_parser](mythroad/src/mr_do.c)选择二进制 undump 或源码 parser；因此源码入口与 `ESC MRP` 字节码是不同载荷，不能称为改魔数字节码。`[实测]` 当前 mrpx WASM 直接启动了上述 gzip 源码包；用本工具解包、重打包后文件逐字节相同，重打包版本也独立启动并绘制同一画面。画布为 240×320，背景像素 `(8,20,24)`，符合 RGB565 量化；两次均检测到 222 个红色像素。原包和重打包的浏览器日志及画布统计分别保存在 [证据 JSON](../../build/mrp-dialect-evidence/user-demo-evidence.json) 和 [重打包证据 JSON](../../build/mrp-dialect-evidence/user-demo-repacked-evidence.json)。

同一 WASM 也直接启动了本工具生成的 **无 `mythroad` 条目、未压缩源码入口**探针包，并执行了 31 个片段；这不证明其他版本或菜单导入流程接受该布局。测试使用的是平台自身的 `cfunction.ext` Guest，不是说模拟器可脱离原生 Guest 运行。详细环境、哈希和方言结果见 [Lua 差异](LUA5_DIFFS.md#73-wasm-源码方言与事件探针)。

`[实测]` 现有 `scan` 面向入口字节码常量表，不解析源码入口：对 gzip 源码样本报告 `Not an MRP chunk` 并分类 C，对未压缩源码探针也分类 C。C 在此表示**扫描器不支持**，不是运行失败或原生扩展依赖；不要未经源码解析和依赖分析就改判为 A。结果见 [本地扫描档案](../../build/mrp-dialect-evidence/source-scan-check/mrp_catalog.json)。

## 2. 压缩与完整性

| 全部索引项 | 数量 | 可得结论 |
|---|---:|---|
| 新式 gzip 完整解压且 CRC/长度通过 | 96,629 | 已用受限 zlib 流完整验证 |
| gzip 头但验证失败 | 3 | DEFLATE 完整、原始长度一致，**CRC 不一致** |
| 其他/原始数据或 raw-deflate | 224 | 无 gzip/zlib 标志；受限完整 raw-deflate 探测为 0 个 |
| 合计 | 96,856 | 非 664 个应用包的压缩计数 |

3 个 CRC 异常分别为 `box.mrp:box_n.bmp`、`shot.mrp:shot_sea.bmp`、`txz.mrp:backdrop.bmp`。例如前者 trailer CRC 为 `fb1191f9`，解压后计算为 `ef79d668`，长度均为 92,640。**源码：**[mr_unzip.c](mythroad/mr_unzip.c)只记录 CRC/长度错误后返回成功，不能由此证明内容没有损坏。工具默认拒绝；`--allow-bad-gzip-crc` 只在校验失败时显式启用、仍检查 DEFLATE 完整性及长度，并在终端和 manifest 记录风险。若内容被编辑再压缩，新 CRC 会按新内容计算。

无签名的 raw-deflate 与任意原始字节不能普遍可靠区分；零个通过探测不等于证明所有其他历史数据都是未压缩。`--raw-index` 是用户提供的 1 起始索引，不做猜测。该 VM 的 `mr_get_method` 识别新/旧 gzip；可选宏还支持 PKZIP local header，其他数据原样返回。它**不因 Python 工具支持 zlib/raw-deflate 就自动支持这两种格式**。工具识别旧 gzip/PKZIP 标志但当前明确报不支持；本次 224 项未发现这些标志。

## 3. MRP Lua dump

**源码：**[mr_undump.c](mythroad/src/mr_undump.c)及 [mr_user_number.h](mythroad/src/h/mr_user_number.h)。语料选择的 663 个入口中，662 为 `0x80`，1 为 `0x50`，均以 gzip 存储。第 664 包没有精确入口；不能把它计为版本解析失败。

```text
00  1b 4d 52 50       签名 ESC MRP
04  vv                版本，加载器接受 0x50..0x80
05  ee                1 小端，0 大端
06  ...               0x50 有宽度测试字段；>0x50 直接开始顶层 Proto
```

`0x50` 附加 8 个单字节宽度 `04 04 04 06 08 09 09 04`，然后以 chunk 字节序存储 `int32 31415926`。`0x80` 不携带这些宽度，因此本工具只按经语料验证的 **32 位 `int` / `size_t` / 指令 / 数值**模型解释，而不声称从头中自动探测模型。归档实现启用 `USE_INT`；标准 Lua 5.0 默认 `lua_Number` 是 `double`。

顶层及每个子 Proto 依次为：

1. `u32 size + size bytes` 源名（0 表示继承父源名；非 0 的长度包含 NUL），`i32 lineDefined`；
2. `u8 nups, numparams, is_vararg, maxstacksize`；
3. `i32` 行号数及对应 `i32[]`；`i32` 局部变量数，每项为名称字符串、`i32 startpc, endpc`；`i32` upvalue 名称数及字符串数组；
4. `i32` 常量数；各项为 `u8 tag` 加值：0 nil、3 有符号 32 位数、4 上述长度字符串；
5. `i32` 子 Proto 数及递归数据；
6. `i32` 指令数及对应 32 位指令。

源名是 Proto 字符串，不是额外的加密/封装。例如 `0x80` 后的 `0a 00 00 00 40 73 74 61 72 74 2e 6d 72 00` 是 `@start.mr\\0`。`=(none)` 等源名也存在。Lua loader 会按配置字节序读取和翻转，完成反序列化后还可校验代码；Python 解析器额外限制长度、深度及尾随字节，**成功解析不等于 VM 执行成功**。完整指令表见 [Lua 差异](LUA5_DIFFS.md)。

## 4. 图像、音频与字库

### 4.1 已确认的无头位图示例

`.bmp` 后缀不证明是 Windows BMP。`tetris.mrp:tetris_n.bmp` 解压后 57,600 字节，前 16 字节为 `91 eb` 重复，没有 `BM` 文件头。其入口 Proto 的 PC 715–723 明确装入参数：名称 `tetris_n.bmp`、`x=0, y=0, w=240, h=120, max_w=240`。因此 `240 × 120 × 2 = 57,600`，与 [BitmapLoad](mythroad/mythroad.c)的 `uint16` 行索引一致；按小端 RGB565、从首行开始转换后，目视得到正常的俄罗斯方块标题图。

`tetris_b.bmp` 是 81 × 320 × 2 = 51,840；`number.bmp` 是 19 × 190 × 2 = 7,220。透明绘制模式使用**第一个像素作为色键**；默认复制模式不透明。`focus.bmp` 的入口参数为 198 × 39，而数据仅 15,048 字节（相当于 198 × 38 × 2）；快速分支未验证该长度，原因及实际显示后果**待验证**。不要把此格式、尺寸推论外推到所有 `.bm`/`.bmp`。

`[官方文档]` `mr_drawBitmap` 描述的是传入内存中的行优先 RGB565，不是通用磁盘文件格式。`[实测]` 社区归档的扫雷 C 源码附带四张标准 24 位 Windows BMP 输入图；打包后格式尚未验证。具体尺寸和来源见 [文档笔记](OFFICIAL_DOCS_NOTES.md)。

### 4.3 `gb16.uc2`

**源码 + 实测：**`assets/runtime/mythroad/system/gb16.uc2` 为 2,097,152 = 65,536 × 32 字节。字符 id 是 UCS-2/Unicode BMP 码点；每字符 16 行，每行 2 字节，大端取位、高位在左，偏移 `codepoint * 32`。GBK 文本先通过编码表转换为 UCS-2 BE，不是直接把 GBK 区位号乘 32。ASCII 0–9 的十个字形及 U+4E2D、U+6C49 按该方法人工目视成形。U+0000..0009 是控制码槽，不代表十个可打印字符；其置位数为 `0,11,12,12,13,16,8,30,98,0`，U+FFFF 槽全零。字形来源与完整语义不由文件名保证。

`[归档文献+实测]` fontmaker 自带的另一套样本使用 `fun_N.bin`/`fgb_N.bin` 五字节索引与可变字宽 `fpoint_N.bin`，并非该 `gb16.uc2` 结构；已核对三个 Unicode 索引各 208 个记录的边界及点阵长度。具体字节和来源见 [文档笔记](OFFICIAL_DOCS_NOTES.md)。文档的紧凑点阵契约与当前 DSM ASCII 槽宽之间存在构建配置层面的潜在差异，尚未通过真实渲染验证。

## 5. 嵌套包与限制

82 个以 `.mrp` 命名的资源在还原后为 `MRPG`，分布于 52 个外层包；数量不代表唯一内容。加载器的 `*A` 和 `$` 选择已注册/RAM 整包，并不证明普通路径可自动逐级穿透包中包。非 `MRPG` 包、其他数字模型、加密、一般图片容器及已损坏内容均需新样本验证。
