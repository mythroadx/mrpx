# ESP32-S3 移植阶段 0：扫雷包字节码确认

## 1. 工具与复现

本阶段只分析资源与字节码，不执行游戏、不启动网络、不修改现有 Guest 或建立 ESP-IDF 工程。

完整工具：[mrp_bytecode.py](../../tools/mrp_bytecode.py)。它复用现有 MRP 索引解析器，默认按顺序寻找 `start.mr`、`start.m`，也可用 `--entry` 指定资源名。

在仓库根目录运行，输入路径替换为实际文件：

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
python tools\mrp_bytecode.py "..\vmrp.github.io-master\public\mrps\winmine.mrp" --output build\esp32-stage0\winmine\start.mr
python -m unittest discover -s tests -p test_mrp_bytecode.py -v
```

工具输出包与解压内容的 SHA-256、索引和数据偏移、压缩格式、前 64 字节 hex，以及每个字节的解释候选；输出文件就是未经改写的解压字节。`--output` 必须指定新文件，已有文件不会覆盖。

支持单流 gzip、zlib、raw-deflate，以及以 MRP/Lua 魔数开头的未压缩字节码。解压上限为 16 MiB；校验失败、截断、尾随数据及串联压缩流显式报错，已识别的 gzip/zlib 不降级猜测其他格式。无法识别的未压缩/加密数据不会冒充解压成功。

头部解释限定为 MRP `0x80` 的 32 位目标布局，不是完整字节码验证器或通用游戏依赖分析器。旧式无索引包不在现有索引解析器的支持范围内。仅列出 `.ext` 文件名不能证明有依赖或无依赖；下文的调用链来自对此样本的额外静态追踪。

## 2. 实测格式结论

### 样本身份与定位

结论仅针对用户提供的这个 `winmine.mrp`，不能推广到所有同名扫雷版本。

| 项目 | 实测结果 |
| --- | --- |
| 包大小 | 11,680 字节 |
| 包 SHA-256 | `4bd619124c409417cbcd1721b11e09f8e13f915c1b87d97a8a0669467477ffd0` |
| 索引范围 | `[0xF0, 0x18C)` |
| `start.mr` 压缩数据偏移 | `0x19D`，即 413 |
| 压缩格式与大小 | gzip，1,739 字节 |
| 解压大小 | 4,536 字节 |
| 解压 SHA-256 | `3d40478ec046678ef9e87ea74c96ed4edc829428fb28b0a34f8c7b914ae2c367` |

有两个与最初指南表述不同、会影响提取代码的细节：

1. 包头 `0x04` 的值是 `0x184`，**索引结束位置是该值加 8**，不是直接使用 `0x184`。这与 [_mr_readFile](mythroad/mythroad.c) 的 `headbuf[1] + 8 - headbuf[3]` 一致。
2. 索引条目的 `offset` 已直接指向 gzip 数据，不应再跳过一次文件名。这个样本在该偏移之前确有记录前缀：

   ```text
   0x18C: 09 00 00 00                       名字长度
   0x190: 73 74 61 72 74 2E 6D 72 00        start.mr + NUL
   0x199: CB 06 00 00                       压缩数据长度 1739
   0x19D: 1F 8B 08 ...                      gzip 数据
   ```

### 解压后的前 64 字节

```text
0000: 1B 4D 52 50 80 01 0A 00 00 00 40 73 74 61 72 74
0010: 2E 6D 72 00 00 00 00 00 00 00 00 04 2A 00 00 00
0020: 02 00 00 00 02 00 00 00 02 00 00 00 02 00 00 00
0030: 34 00 00 00 28 00 00 00 3C 00 00 00 3C 00 00 00
```

| 偏移 | 按归档加载器解释 |
| --- | --- |
| `0x00..0x03` | `ESC MRP`，即 `\x1bMRP` |
| `0x04` | `0x80`，MRP chunk 格式版本，不是 Lua 8.0 |
| `0x05` | `1`，小端序 |
| `0x06..0x09` | 32 位源文件名长度，10，包含 NUL |
| `0x0A..0x13` | `@start.mr\0` |
| `0x14..0x17` | 根函数 `lineDefined = 0` |
| `0x18` | `nups = 0` |
| `0x19` | `numparams = 0` |
| `0x1A` | `is_vararg = 0` |
| `0x1B` | `maxstacksize = 4` |
| `0x1C..0x1F` | 行号表条目数，42 |
| `0x20..0x3F` | 前八个 32 位行号：2、2、2、2、52、40、60、60 |

**对该入口无需额外去壳、解密或改魔数。** gzip 解压后就是归档 VM 能识别的 MRP chunk 格式。额外的静态结构解析按 32 位整数数值/长度/指令布局遍历函数、常量和代码，恰好消费全部 4,536 字节；这不等于已经在 ESP32 或原生重编 VM 上运行成功。

## 3. ESP32 VM 需要的预处理

保留这条数据通路：

1. 按 MRP 索引获取资源数据的偏移和长度。
2. 对此包执行一次 gzip 解压，校验错误必须上报；不要把工具为研究而支持的其他压缩格式当成本包的需求。
3. 将完整 `\x1bMRP...` 内容交给归档 VM 加载器；不跳过 6 字节头，不改成 `\x1bLua`。

源码对应：

- [mythroad.c](mythroad/mythroad.c)：`_mr_readFile` 读取索引定位的数据，调用解压逻辑。
- [mr_auxlib.c](mythroad/src/lib/mr_auxlib.c)：`mr_L_loadfile` 将 `_mr_readFile` 的结果交给 `mrp_load`。
- [mr_do.c](mythroad/src/mr_do.c)：二进制分支调用 `mr_U_undump`。
- [mr_undump.h](mythroad/src/h/mr_undump.h)：定义 MRP 魔数及 `0x50..0x80` 版本范围。
- [mr_undump.c](mythroad/src/mr_undump.c)：`LoadHeader` 对大于 `0x50` 的版本省略旧 Lua 头部的类型宽度及数值格式测试字段，随后 `LoadFunction` 读取函数体。

原生编译时仍须保持正确的 32 位序列化布局。[mr.h](mythroad/include/mr.h) 包含的 [mr_user_number.h](mythroad/src/h/mr_user_number.h) 当前选择 `USE_INT`。`Instruction`、`size_t` 的读取宽度及字节序也须对齐实际资源，不能盲用 64 位 PC 数据模型。

这份 VM 是 Lua 5.0 派生版，另有四条位运算指令。直接换官方 Lua 5.0 并只改魔数，不是已验证的兼容方案。当前桌面宿主仍执行 ARM Guest；阶段 1 还需要建立归档 VM 的原生构建，不能把当前桌面运行成功当作它已原生编译成功。

## 4. 阶段 2 的阻碍：此扫雷版本依赖 ARM EXT

包内还有 `cfunction.ext`：压缩数据偏移 `0xDA3`，压缩大小 8,189 字节，解压大小 16,104 字节。

解压 SHA-256：`0ab9d63ce76cd2e6f6ab34fc27561e6fc8ca94562e842525733d6ddbcef4dd48`。

其前缀为 `MRPGCMAP`，后接 `10 40 2D E9 ...` 的 ARM 入口指令。它与宿主加载的主运行时是不同文件。

不只是“打包了一个可能不用的扩展”。对解压入口的静态追踪发现：

| 解压 `start.mr` 中的偏移 | 证据 |
| --- | --- |
| `0x1120..0x1124` | 根函数把第一个子函数保存为全局 `_mr_c_load` |
| `0x117C..0x1180` | 根函数取得并调用 `_mr_c_load` |
| `0x02B1..0x02C1` | 子函数调用 `_strCom(601, "cfunction.ext")`，结果保存到 `_mr_c_buf` |
| `0x02D1..0x02E5` | 缓冲区存在时调用 `_strCom(800, _mr_c_buf, 0)` 并返回结果 |
| `0x1194..0x11A4` | 初始化成功路径通过 `_strCom(801, "", 0)` 调用扩展 |
| `0x11AC..0x11B0` | 失败路径调用 `Exit` |

对应 [mythroad.c](mythroad/mythroad.c) 中 `_mr_TestCom1` 的 `601`（读资源）、`800`（加载并进入原生扩展）、`801`（调用扩展事件入口）。

因此，在“本阶段不支持 ARM EXT”的约束下，**这个具体扫雷包不适合作为首个纯脚本游戏验收样本**。不能只删除包内 EXT、把加载函数改成成功返回，或跳过启动判断来声称扫雷可运行。应由用户提供另一份纯脚本版本或选择其他已确认无原生依赖的包；其他候选包尚未在本阶段检查。
